# TLS Key Complexity & CA Renewal — applicability

The `spec.tls.keyComplexity` (RSA/ECDSA algorithm selection) and
`spec.tls.caRenewalDays` (CA-specific renewal window) fields currently apply to
**Elasticsearch only**.

## Why

- **Elasticsearch** certificates are generated by the
  `operator-sdk-extra/v3` library (`selfmanaged` / `selfmanaged/pernode`
  backends), which support ECDSA (`KeyAlgorithmECDSA` + `Curve`) and the
  full `TLSSpec` surface. The operator maps `keyComplexity` and
  `caRenewalDays` onto those backends.

- **Kibana, Logstash and Filebeat** single-certificate TLS generation is still
  handled by the legacy `github.com/disaster37/goca` library. `goca`'s `key`
  package is RSA-only (`rsa.GenerateKey`; no ECDSA/curve support), so wiring
  `keyComplexity` into those apps would require re-implementing ECDSA key
  generation — out of scope for the current migration. `caRenewalDays` is also
  not wired there: those apps use a single leaf cert with no CA rotation saga.

## Migration path

When `goca` is replaced by the library's certificate backends for the
single-certificate apps (the long-term plan already adopted for Elasticsearch),
`keyComplexity` / `caRenewalDays` can be mapped onto `TLSSpec` for Kibana,
Logstash and Filebeat the same way they are for Elasticsearch. Until then, these
two fields have no effect on those CRDs.
